<technical_details>
**Deterministic System Architecture:**
- The forever-song system is 100% deterministic: same (date, time, location) always produces identical music
- This is enabled by seeded RNG: each voice uses distinct seed offsets (main=index, bass=+1M, pad=+2M, arpeggios=+3M)
- Enables freezing time and generating human-readable scores for analog performance

**Key Astronomical Cycles:**
- **Key changes**: Every lunar cycle (~29.5 days) — 12 roots × 7 modes cycling
- **Time signature**: Changes throughout day via Venus synodic clock (but continuous sampling, not discrete jumps)
- **Dynamics**: Continuous, driven by sun altitude (diurnal cycle), Venus altitude, Jupiter altitude, visible planet count
- **Beat-to-beat melody**: Deterministic per beat, driven by cosmos state + seeded RNG

**Data Serialization (Critical Bug Fix):**
- Original approach: Passing entire cosmos object through postMessage (worker → UI thread) failed
- Issue: Complex objects with getters/setters don't serialize cleanly across thread boundary
- Solution: Extract only needed numeric values into simple `CelestialData` struct with plain properties (altitude, azimuth as numbers)
- Lesson: When using workers, always serialize data explicitly; don't rely on object passing

**Field Name Quirks:**
- Sun uses `elevation` not `altitude` (different from planets/moon)
- Moon uses `phase` (not `illumination`); illuminationPercent exists but is percentage not normalized
- Defensive null checks required: `c.moon.phase?.value ?? 0.5` pattern throughout

**Music Theory Implementation:**
- Bass scale degree selection: `combined = (moonPhase * 0.7 + jupiterAltitude * 0.3) % 1.0`
- Moon phase drives slow walk (70% weight), Jupiter altitude adds variation (30% weight)
- Octave selection: 75% octave 2, 25% octave 3 for variety
- Scale pool: All unique pitch classes extracted from scale.intervals

**Unanswered Questions:**
- What time resolution do we want for score export? (per beat? per bar? per hour?)
- Should the score include performance timing/rubato or just the note sequence?
- How to handle continuous dynamics in written score (should we discretize into sections)?
</technical_details>
