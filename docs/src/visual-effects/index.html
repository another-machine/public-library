Prototype — not a package

One interface for generators and filters

AVVA's renderer synthesises images from uniforms. A CRT filter transforms an image it is given. They look like different kinds of thing, and that is why the shader work in each has stayed stuck to the app it was written for. The only structural difference between them is whether a pass samples an incoming image — so that is the one flag this design turns on.

inputs: { source?: boolean; feedback?: boolean }

A pass that sets source is a filter and receives uSrc. A pass that does not is a generator. The chain feeds each pass's output to the next either way, so the CRT pass below is the same object whether it is finishing a generated field or a video file you drop in.

The three passes

Between them they exercise every part of the interface, which is the whole reason there are three. 

field   generator + feedback + compile-time defines
        N_HUES is a #define, so moving the hues slider
        recompiles rather than branching per fragment.
        This is AVVA's shape.

bloom   filter + a private quarter-res ping-pong buffer
        + a four-step draw hook. The small stand-in for
        chladni: proves buffers/draw/mid-pass swapping
        without porting 262k particles to find out.

crt     filter, single draw. The NTSC demo's fragment
        shader, essentially unchanged.

What changed around the CRT shader

The shader body was always the good part of that demo. What it was wrapped in was not. 

ghosting    was: a 2D-canvas copy of the previous INPUT,
            re-uploaded every frame — so trails could
            never accumulate, and every frame paid a CPU
            readback at source resolution.
            now: uPrev, a ping-pong of this pass's own
            previous OUTPUT.

scanlines   was: sin(vUV.y * uResolution.y), so stripe
            frequency tracked device pixels — it changed
            on a retina display and again on resize.
            now: a line count.

lifecycle   was: rAF started in the constructor, no stop,
            no dispose, no context-loss handling.
            now: dispose(), and a contextLost flag.

Resolution

The open question from the design sketch, resolved here rather than left for later. Every pass gets two: uRes is the buffer this pass renders into, uOutRes is the chain's final output. Anything keyed to signal resolution — grain, blur taps, bloom — must use the former, or a pass at scale: 0.5 silently changes its own look. The bloom pass runs its bright-pass and blur at quarter res and is the case that proves it.

Uniforms are typed by the program, not the caller

uniforms() returns a plain bag of names to values. A Float32Array is a float[] or a vec3[] depending on what the shader declared, and only the shader knows — so the chain reads the types back off the linked program. A pass may hand over more than a given step uses; names the compiler dropped are ignored.

No domain data anywhere

The params below are neutral: energy, motion, x, y, impulse. Here they come from a few LFOs. In AVVA they would come from an AudioFrame through a small adapter at the call site, and in a video tool most of them would sit at rest. The chain cannot tell the difference, which is the property that makes it extractable at all.

Slot colours divide the wheel into equal sectors of perceptual hue rather than display hue — the property @amplib/color exists to provide. Equal steps of HSV hue do not look equal, and a palette spaced that way comes out visibly lopsided.
